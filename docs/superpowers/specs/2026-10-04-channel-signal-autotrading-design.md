# Исполнение сигналов стороннего Telegram-канала через существующий движок автотрейдинга

## Контекст и мотивация

Отдельно от собственного детектора импульсов (`analyzer.py`) пользователь хочет подключить
внешний источник входов: Telegram-канал/группа (`-1002487960768`), где другой автор тоже
торгует на манипуляциях рынка и публикует сигналы (тикер + направление). Как только приходит
такой сигнал, бот должен войти в сделку **по уже существующей стратегии** — тот же риск-
менеджмент, та же сетка TP (15/20/25% + 40% трейлинг-шандельер на TP4), тот же ATR-стоп, —
просто точка входа задаётся не своим детектором, а чужим сигналом.

Источник сигналов — paper trading (виртуальный баланс), как и весь остальной автотрейдинг
сейчас. Переход на реальные деньги этой спекой не рассматривается.

## Разбор реального формата канала

На 9 реальных сообщениях канала обнаружено три типа контента:

- **Тип A — «ЗАХОДИМ В МАНИПУЛЯЦИЮ»** (6 из 9 примеров: XAI, PHA, ARK, BTW, US, CAP).
  Устойчивый шаблон: заголовок, затем строка `<ТИКЕР> <SHORT|LONG> - <обоснование>`, без
  конкретных цифр стопа/тейка.
- **Тип B — пересланные от другого автора ("Кристина")** (MARSCOIN, CELO, NIGHT). Формат:
  `заходим в позицию <ТИКЕР> <long|short>` ИЛИ `давай <шорт|лонг> на <ТИКЕР>` (порядок слов
  варьируется), плюс плечо/маржа/конкретная цена тейка — эти поля игнорируются, бот берёт
  только тикер и направление.
- **Тип C — «СДЕЛКА НА СПОТ»** (1 из 9: UAI). Спотовая рекомендация на недели вперёд, без
  плеча. **Не входит в область этой фичи** — не подходит под intraday-модель со стопом по ATR.

**Решение владельца:** исполняются только типы A и B. Тип C игнорируется парсером как
нераспознанный (попадает в общий "не распознано, залогировано" путь, см. ниже).

Направление сигнала напрямую соответствует существующей семантике бота: автор SHORT'ит
монету, которая недавно резко выросла (= фейд пампа, `direction="up"` во внутренних терминах
бота), автор LONG'ит монету после снижения (= фейд дампа, `direction="down"`). Это позволяет
переиспользовать уже существующий выбор риск-процента по направлению
(`_risk_percent_for_direction`, `live_trading.py:123`): SHORT → `PUMP_RISK_PERCENT` (1%),
LONG → `DUMP_RISK_PERCENT` (4%) — без новых констант.

Сообщения о закрытии/отмене сигнала у канала не встречены и не парсятся — выходы полностью
управляются собственным движком бота (ATR-стоп, TP1-3, трейлинг TP4), независимо от того, что
дальше пишет автор канала.

## Компонент 1: парсер (`channel_signal_parser.py`, новый файл)

```python
@dataclass
class ParsedChannelSignal:
    ticker: str       # "XAI", без USDT
    direction: str     # "long" | "short" (терминология канала, не бота)
    raw_text: str
```

`parse_channel_signal(text: str) -> ParsedChannelSignal | None`:

1. Матчер типа A: ищет строку-заголовок, содержащую «ЗАХОДИМ В МАНИПУЛЯЦИЮ» (регистронезависимо),
   затем на следующей непустой строке — `^([A-ZА-Я0-9]{2,10})\s+(SHORT|LONG|ШОРТ|ЛОНГ)\b`.
2. Матчер типа B, пробует по всему тексту (не только первой строке, т.к. встречаются вступления
   вроде «Так, »):
   - `заходим в позицию\s+([A-ZА-Я0-9]{2,10})\s+(long|short|лонг|шорт)` (тикер → направление)
   - `давай\s+(шорт|лонг)\s+на\s+([A-ZА-Я0-9]{2,10})` (направление → тикер)
3. Если ни один матчер не сработал — `None`. Сырой текст логируется на уровне INFO с префиксом
   `channel_signal: не распознано:` — чтобы при появлении нового формата (ожидаемо, как уже
   было с форекс-ботом) было видно, что именно бот пропустил, и расширить парсер.

Парсер — чистая функция без сети и без состояния, полностью покрывается юнит-тестами на
реальных примерах из этого диалога (включая оба порядка слов в типе B и отрицательные кейсы:
тип C и случайная болтовня возвращают `None`).

## Компонент 2: слушатель (`channel_signal_listener.py`, новый файл)

Telethon-клиент на пользовательской сессии (как в `tg-forex-signal-monitor/auth_telethon.py`):

- `TG_API_ID` / `TG_API_HASH` — те же переменные, что уже использует форекс-бот (личные данные
  приложения с my.telegram.org, не привязаны к конкретному боту).
- Файл сессии — на Railway Volume (переживает редеплои), путь через `TG_CHANNEL_SESSION_PATH`.
- Разовая авторизация — отдельный скрипт `auth_channel_session.py` (адаптация
  `auth_telethon.py`), запускается один раз на Railway (не локально — MTProto заблокирован в
  сети владельца).
- `CHANNEL_SIGNAL_SOURCE_ID = -1002487960768` — ID канала, константа в `config.py`.

Обработчик `on_channel_message(event)`:
1. Берёт `event.message.text` (raw-текст, без UI-обвязки вроде «Переслано от …» — это
   Telegram-клиентская отрисовка, в `message.text` её нет).
2. `parse_channel_signal(text)`.
3. Если распознано — вызывает `live_trading.handle_channel_signal(session, chat_id, ticker,
   direction)`.

Основная логика вынесена в `on_channel_message` как обычную тестируемую async-функцию,
принимающую текст напрямую — обвязка Telethon (`@client.on(events.NewMessage(...))`) вокруг
неё тонкая и не покрывается юнит-тестами (аналогично тому, как в `main.py` разделены
`on_kline_close` и сетевая подписка).

Задача запускается в `main.py` как ещё один `asyncio.gather(...)`-таск, рядом с торговым
циклом, отчётом и веб-сервером. Падение задачи (потеря сессии, сетевая ошибка) логируется и не
должно ронять остальные задачи — оборачивается в try/except с перезапуском через паузу (та же
схема, что уже используется для устойчивости других фоновых циклов бота).

## Компонент 3: исполнение (`live_trading.py`, новая функция `handle_channel_signal`)

```python
async def handle_channel_signal(session, chat_id: int, ticker: str, channel_direction: str) -> dict | None:
```

Шаги:
1. `direction = "up" if channel_direction in ("short", "шорт") else "down"`.
2. `symbol = f"{ticker}USDT"`.
3. Резолв биржи: проверка символа в уже существующем кэше торгуемых символов Binance
   (`fetcher.get_tradable_symbols`), при отсутствии — Bybit (`bybit_fetcher.get_bybit_tradable_symbols`).
   Если нигде нет — лог + `return None` (сигнал пропущен, монета не торгуется на наших биржах).
4. Проверка чёрного списка (`SYMBOL_BLACKLIST`) — как в `handle_new_impulse`.
5. Проверка конфликта: `symbol in _pending_setups or symbol in _open_positions or symbol in
   _reserved_symbols` → `return None` (пропуск сигнала, по решению владельца — не открываем
   параллельный слот, если монета уже торгуется нашим детектором или другим сигналом канала).
6. Проверка `profile.is_active` и лимита `max_concurrent_trades` — как в `handle_new_impulse`.
7. Бронирование `_reserved_symbols`, как в существующем коде (защита от гонки при параллельных
   сигналах).
8. Получение `atr_1h` и `atr_15m` — те же вызовы, что делает `impulse_analysis.analyze_impulse`
   внутри (`market_data.fetch_klines` + `indicators.atr`), без funding/climax-проверок — они
   специфичны для организального детектора и к чужому сигналу не применяются.
9. `magnet_levels` считаются тем же способом, что и в `handle_new_impulse` (не обязательны для
   работы `_create_pending_reversal_setup` — если не передать, посчитаются внутри неё заново).
10. `trading_storage.create_trade_signal(chat_id, symbol, exchange, impulse_direction=direction,
    classification="reversal", source="channel")` — см. схему ниже.
11. Отдельное Telegram-уведомление (НЕ переиспользует `trade_signal_ux.announce_and_execute` —
    тот текст заточен под организальные импульсы с `window_start_price`/уровнем, которого тут
    нет): `"📡 Сигнал из канала: {ticker} {SHORT|LONG} — вхожу..."`.
12. `execute_setup(session, chat_id, symbol, exchange, direction, classification="reversal",
    current_price, window_start_price=current_price, profile, analysis={"atr_1h":...,
    "atr_15m":..., "magnet_levels":...}, signal_id)` — та же функция, что уже используется для
    органических reversal-сетапов. Дальше всё (двухчастный вход, стоп, TP1-3, трейлинг TP4)
    идёт по уже существующему, не изменяемому коду.

## Данные: новая колонка `source` в `trade_signals`

`ALTER TABLE trade_signals ADD COLUMN source TEXT NOT NULL DEFAULT 'analyzer'` — у сигналов из
канала значение `'channel'`. Ничего в существующей логике не меняет (значение по умолчанию
сохраняет текущее поведение для всех старых и органических сигналов), но даёт возможность
позже честно посчитать: сигналы этого канала через нашу систему риск-менеджмента доходнее
органических или нет. Если не нужно — убираю, фича работает и без этого поля.

## Не реализовано / сознательно вне рамок

- Сообщения о закрытии/отмене сигнала канала не парсятся — выход только через собственный
  движок бота.
- Тип C (спот) не исполняется.
- Реальные деньги — не рассматриваются, только paper trading.
- Несколько каналов-источников — не рассматривается, только один конкретный ID.
- Если формат сообщений канала изменится, старый парсер не узнает новые кейсы автоматически —
  это ожидаемо (как и у форекс-бота), для расширения потребуется отдельная правка на основе
  залогированных «не распознано» сообщений.
